# Decisions

Choices the spec docs don't settle, made during the build. Newest at the bottom of each phase.

## Phase 1

**27 Oct 2026. Python 3.12, Django 5.2 LTS.** The project conventions name Python 3.12; the laptop also has 3.14, so the venv is pinned with `py -3.12`. Django 5.2 is the current 5.x LTS.

**27 Oct 2026. No login and no Django admin in Phase 1.** The app binds to localhost on the laptop and has one user, so `contrib.auth` and `contrib.admin` are left out. A login arrives in Phase 2, when Tailscale exposes the app to the iPad. All CRUD is on Downbeat's own pages, as the kickoff asks.

**27 Oct 2026. Theme generated from LooseLeaf's token compiler.** `tools/build-theme.mjs` sets the neutral ramp to zero chroma (greyscale chrome) and the action and accent hues to the same indigo (hue 270), so the interface has exactly one accent. One contrast pair falls short: link text on the dark surface is 4.15:1 against a 4.5 target, the same shortfall LooseLeaf's defaults have. Links are rare in the room view; revisit at the surface pass. A configurator export can replace the bundle at any time.

**27 Oct 2026. Navigation shows only areas that exist.** The desk navbar lists Today and Settings in Phase 1 (Plan once the seating editor exists). Sweep and Pupils appear when their phases build them, so no link leads to an empty page.

**27 Oct 2026. Checklist items and flag types are not in the Phase 1 first-run setup.** BUILD_ORDER's Phase 1 paragraph says the setup creates "the timetable, note types, checklist items and flag types", but ChecklistItem and FlagType are Phase 3 tables, the project conventions say not to scaffold later phases' models, and the kickoff says no flags. The setup wizard gains those steps in Phase 3.

**27 Oct 2026. First-run setup is one page, saved atomically.** The rule is "if no Timetable exists, redirect to setup". A multi-page wizard that saved the timetable first would release the redirect before note types and a room existed. One page with three sections (timetable and periods, note types, first room) saves everything in one transaction or nothing. Blank spare rows are ignored; at least one period and one note type are required. Placeholders show examples but no value is pre-filled.

**27 Oct 2026. The active timetable is the newest one.** The data model says "one active timetable; keep old ones for history" without an active field. `Timetable.active()` returns the most recently created, so no extra column is needed. A new timetable is made active by creating it.

**27 Oct 2026. Note type icon is a short text field.** An emoji or symbol the teacher types (★, ✎, ⚠). No icon library and no images; it renders as the seat badge.

**27 Oct 2026. Session carries a `period` label.** The data model gives Session a date and a nullable slot, but Today has to order sessions and know which one is live, and a one-off or moved session has no slot to read the period from. Session stores the period label, copied from its slot when generated and editable per day like the room. Times come from the active timetable's periods by label. Co-curricular sessions at lunch or after school use periods the teacher adds to the timetable ("Lunch", "After school").

**27 Oct 2026. Slots and sessions refer to periods by label.** Renaming a period in the timetable doesn't rename the slots that use it; the slots page lists them as using a period the timetable no longer has, with a link to fix each one. This keeps periods as plain JSON, as the data model has them.

**27 Oct 2026. Week A/B is chosen when generating.** The timetable doesn't record which calendar week is A. The generate form (and `manage.py generate_sessions --first-week`) asks which week the first date falls in, and alternates from that week's Monday. Holidays are handled by generating one half term at a time; generating again over the same dates never duplicates or overwrites a session.

**27 Oct 2026. Pasted class lists keep the surname initial only.** Pupils are quickest to add by pasting one per line on the class page. The last word on each line is taken as the surname and cut to its first letter, so "Aleya Khan" from a register is stored as "Aleya K" and the full surname is never saved. Lines of one word are skipped and listed back.

**27 Oct 2026. Deleting is guarded where history depends on it.** A class or room with sessions can't be deleted (the sessions will carry notes from step 7 onwards). Deleting a slot keeps its sessions, which become one-offs. Deleting a pupil removes them from every class.

**27 Oct 2026. Pupil keeps the recording permission fields now.** recording_permitted, exemplar_reuse_permitted and recordings_delete_by are fields on the Phase 1 Pupil table in the data model, so they are in the schema and the pupil form from the start, defaulting to off. Nothing uses them until Phase 5.

**27 Oct 2026. The room editor lives under Settings → Rooms.** UX.md's page inventory puts the room editor in Plan, but its Settings list also names rooms, and a room is drawn once and shared by every class. Configured-once work belongs in Settings. Per-class seating plans live under Plan.

**27 Oct 2026. Room stores the teacher position.** The data model has `near_teacher` on Seat but nowhere for the teacher-position marker the kickoff asks for. Room gains nullable `teacher_x` and `teacher_y`. An unplaced marker is drawn at the front centre. `near_teacher` stays a per-seat flag the teacher paints, not a distance computed from the marker, so the teacher decides what "near" means in each room.

**27 Oct 2026. Seats are 80 × 44 canvas units; new rooms default to 900 × 600.** Positions are stored in canvas units and the canvas scales to its container. At the room view's two-thirds of a laptop screen a 900-wide canvas renders near 1:1, so a seat stays close to the 44-point minimum tap size. A larger room can be given a bigger canvas, at the cost of smaller seats on screen. Dragging snaps to 10 units; arrow keys nudge a focused seat.

**27 Oct 2026. Zones are the five fixed choices from the data model.** Front, back, side, carpet, keyboard, or none. They are painted with a brush (choose a zone, tap seats) and show as text in the editor only; the room view doesn't display zones.

**27 Oct 2026. `DOWNBEAT_DB` overrides the database path.** Lets a throwaway database be used for browser checks without touching the real one.

**27 Oct 2026. Seating plans are edited under Plan; tap locks.** The Plan area in Phase 1 is one page of class cards, each listing its plans by room with a "new plan in…" picker. In the seating editor a pupil is dragged from the unseated list or from a seat; dropping on a seated pupil swaps them, or sends them back to the list if the dragged pupil wasn't seated. Tapping a seated pupil locks or unlocks them. A locked seat refuses to give up or take a pupil. The server re-renders the board after every change, so the page can't drift from the database.

**27 Oct 2026. The recycle bin is a drop target; undo lives in the browser session.** Dropping a pupil on the bin (or the unseated list) unseats them. Every move, swap, unseat and lock pushes a snapshot of the touched seats, before the change, onto an undo stack of ten per plan, held in the Django session rather than a new table. Undo is for a desk editing session; nothing in the data model needs it to survive a restart.

**27 Oct 2026. The no-plan fallback copies by zone, ordered from the teacher.** When a class has no plan for a room, a new one copies from the class's most recent plan in another room. Each seated pupil goes to a free seat of the same zone (no zone counts as a zone), and within a zone pupils keep their order outwards from the teacher marker (top to bottom if no marker), so front stays front even when the two rooms face different ways. Pupils with no matching seat are left unseated for the sweep. Locks aren't copied. No class plan elsewhere means a blank plan.

**27 Oct 2026. The plan in force is chosen by date.** `SeatingPlan.current` picks the class's plan for the room whose active_from is on or before the date and whose active_to is empty or on or after it, newest first. Phase 1 gives new plans active_from of today and no end; duplicate-to-reshuffle (Phase 3) will use the dates.

**27 Oct 2026. The canvas is capped at the screen height.** A canvas never grows taller than the viewport minus page chrome, so the whole room and the unseated list are on screen together while dragging.

**27 Oct 2026. Today redirects only when a session is live; `?list` always shows the list.** A session is live when now falls inside its period and it isn't cancelled. Outside lessons Today shows the day in period order (not alphabetical, so P10 follows P9), with the current or next one outlined. The room view's "Today" link adds `?list`, so the teacher can always reach the list mid-lesson without being bounced back.

**27 Oct 2026. Next session means the next one that isn't cancelled.** Later the same day first, then the following days (up to 60 days ahead). The N key and the "Next ›" button in the bar both go there. N lives in canvas.js's room-view mode, keeping to two hand-written JS modules, and is ignored while typing or while a sheet is open.

**27 Oct 2026. The room view's no-plan offer is one quiet line.** When the class has no plan for the session's room, a single muted line above the canvas offers "Seat by zone from M2" (or "Start a blank plan") as one tap that returns to the room view. It isn't red and doesn't count anything, and the room view works without it: unseated seats are simply empty.

**27 Oct 2026. The plan strip shows the period and its times until Phase 4.** There are no lesson plans yet, so the strip reads "P3 · 10:50–11:50". It becomes current-and-next activity, and the Log/Plan flip, when PlanActivity exists.

**27 Oct 2026. The picker button arrives with the picker (step 8).** The bottom bar in step 6 carries the Today link, session name and next session. No control appears before it does something.

**27 Oct 2026. Free text is a Note with no type.** Note.note_type is nullable; an empty type means free text, shown with ✎. The free-text form has a "Needs action" tick, the only choice in the whole note flow, because it is already the one form allowed.

**27 Oct 2026. Note leaves out the fields later phases need.** Group (Phase 3), voice_path and transcript (no voice notes yet) and promoted_to_mis_at (Phase 6) are added when their features are built, so the Phase 1 table holds nothing unused.

**27 Oct 2026. "Unread" counts a pupil's open actions.** The teacher writes every note, so nothing is literally unread. The counter on the note sheet's name and the dot on the seat show that pupil's actionable notes not yet done, from any lesson. Tapping the counter opens the inbox (all their notes, newest first); nothing else in the room shows past notes.

**27 Oct 2026. Seat badges are this lesson's notes.** A seat shows the icons of notes made for that pupil in this session, so the room shows what has happened this lesson and resets each lesson.

**27 Oct 2026. Notes go to a bin, with undo.** Each Log line has a one-tap remove, which sets a `deleted_at` (a field the data model doesn't list, added so removal is recoverable). An Undo button appears in the Log heading and reverses the last ten adds or removes this lesson, held in the browser session like seating undo. Removed notes vanish from every view.

**27 Oct 2026. Actions carry forward by query.** The Actions sheet lists open actionable notes from this session and from every earlier session with the same class (by date and period order). When a carried note is listed in a later session, `carried_to_session` is set to it, recording where it landed. Done is one tap. The bottom-bar counter is neutral: "Actions" alone when nothing is open, with a plain number otherwise.

**27 Oct 2026. Sessions and note types with notes are protected.** A session with notes can't be deleted (mark it cancelled instead), and a note type that has been used can't be deleted (rename it), so no note loses its lesson or its meaning.

**27 Oct 2026. Unseated pupils are still reachable in the room.** Pupils in the class without a seat in this plan show as a row of names under the room, with the same tap-for-the-sheet behaviour. Otherwise a blank plan or a new pupil would leave someone impossible to note.

**27 Oct 2026. SessionAttendance comes forward from Phase 3.** The picker has to skip absentees, which needs somewhere to record them. The data model's SessionAttendance (session, pupil, present) is added now, in the timetable app. It isn't a register: no row means present. Absence is a toggle beside "Spoken to" at the top of the note sheet (two taps, closes the sheet); an absent seat is faded and its name struck through.

**27 Oct 2026. Spoken to is a toggle.** One tap on "Spoken to" adds a row and closes the sheet; tapping it again on a dimmed pupil removes this lesson's rows, so a mistaken tap is undone the same way it was made.

**27 Oct 2026. "Missed last time" uses the class's previous lesson, and only if spoken-to was used in it.** The highlight (a thicker accent edge) goes to pupils with no spoken-to row in the class's last non-cancelled session. If that session has no spoken-to rows at all, nobody is highlighted, so a lesson where the feature wasn't used doesn't light up the whole class the next time.

**27 Oct 2026. The picker records on every draw and offers "is absent".** Each draw, including "tap to draw again", writes a spoken-to row, as the spec says. Because a name called to an empty chair would otherwise leave a wrong row, the picker shows "<name> is absent": one tap marks them absent, takes back that draw, and draws again. The default pool is present pupils not yet spoken to; when everyone has had a turn it draws from all present pupils. A toggle switches to the whole class. Unseated pupils are included, since the picker draws from the class, not the seats.

**27 Oct 2026. Seat states are data attributes on the seat's marks, styled with `:has()`.** Spoken to, absent and missed are flags on the marks element inside each seat, so the one out-of-band swap that already updates badges keeps every state current without re-rendering seats.

**27 Oct 2026. Projector view is black on white through the light system colours.** The page sets `color-scheme: light` and uses `Canvas`/`CanvasText`, so it stays high contrast with the laptop in dark mode and needs no raw colours. It shows seats, names and a "Front" marker, nothing else: no badges, counts, dimming, absence or highlights. It opens in a new window (to drag onto the projector's display), and its "Full screen" button is the only full-screen control in the app.

**27 Oct 2026. Cover PDF is drawn with reportlab.** A real A4 landscape PDF download, not a print stylesheet, so it can be emailed to cover. It carries the class and room as a title, the room outline, seats with names, the teacher position, and a "Not seated" line listing pupils without a seat. Nothing from notes, spoken-to or attendance. reportlab is pure Python with Windows wheels; it is the only new dependency in Phase 1.

**27 Oct 2026. The overflow menu sits at the right of the bottom bar.** A "⋯" button opens LooseLeaf's dropdown upwards with "Projector view" and "Cover PDF". Neither appears anywhere else on the room view.

**27 Oct 2026. Tests close the phase with an audit file.** Each step's tests went in with the step. `core/tests/test_audit.py` adds the cross-cutting checks: every mutating endpoint refuses GET and returns 404 for unknown rows; the error paths answer cleanly; and 25 seeded random runs of 60 moves, unseats, locks and undos each check that no seat holds two pupils, no pupil holds two seats, and a locked seat never changes under a move. Hypothesis isn't a dependency; seeded `random` keeps failures reproducible.

**27 Oct 2026. Demo data is a command against its own database.** `manage.py seed_demo` builds a disposable school for development: a two-week timetable, three rooms (rows, a keyboard room, the hall), five classes and a co-curricular choir, about 90 invented pupils (first name and initial, from a fixed seed so every run matches), sessions from last week to next, and past lessons with notes timed inside the lesson, open actions to carry, spoken-to rows and absences. One 8X lesson is moved to the hall, where 8X has no plan, to show the zone-copy offer. It is never run by a migration, refuses a database that already has data, and `--reset` refuses the default `db.sqlite3`, so it lives in `demo.sqlite3` via `DOWNBEAT_DB` and the real install still starts at first-run setup.

## Between phases: hardening

**27 Oct 2026. Phases are built in order without waiting for classroom use.** The build order gates each phase on a fortnight of real lessons. The teacher has chosen to have the app completed thoroughly before using it, so phases follow one another in BUILD_ORDER's order, each finished, tested and hardened before the next starts. The "Done when" tests remain the definition of done, checked against demo data until real use begins.

**27 Oct 2026. The data rules are implemented before Phase 2.** Settings → Data and three commands cover the Architecture section's promises. `manage.py backup` copies the live database with SQLite's online backup API, so it is consistent mid-write, converts the copy to a self-contained file, checks its integrity and keeps the newest 30 (`DOWNBEAT_BACKUP_DIR` and `DOWNBEAT_BACKUP_KEEP`; point the folder at OneDrive for the off-laptop copy). `tools/install-backup-task.ps1` registers a nightly Windows scheduled task that also runs at the next start-up if the laptop was off. `manage.py export_json` and "Download everything" give every row as JSON that `loaddata` reads back. "Delete everything" wipes every Downbeat row and browser session after the phrase "delete everything" is typed, and returns to first-run setup; backup files are separate and left for the teacher to remove. Restoring is copying a backup over `db.sqlite3` with the server stopped.

**27 Oct 2026. SQLite runs in WAL mode with IMMEDIATE transactions.** Readers no longer block on a writer, and overlapping writes wait up to 20 seconds rather than failing with "database is locked". This matters from Phase 2, when the iPad's queue syncs while the laptop is in use.

**27 Oct 2026. Per-install secrets and logs live in `local/`.** The secret key is generated on first start into `local/secret_key` (or taken from `DOWNBEAT_SECRET_KEY`), replacing the shared development default. Warnings and errors go to a rotating `local/logs/downbeat.log`. `local/` and `backups/` are ignored by git. DEBUG stays on while the app is served by `runserver` on localhost; Phase 2 replaces that with a proper server and turns it off.

**27 Oct 2026. A double tap never records twice.** Every HTMX button and form that posts disables itself while its request is in flight (`hx-disabled-elt`). An audit test fails if a template adds an `hx-post` without it.

**27 Oct 2026. Lint and CI.** Ruff checks the code (pyflakes, pycodestyle, import order, bugbear, pyupgrade, simplify; Django's `Meta` lists and the British typography in UI text are exempt). GitHub Actions checks out Downbeat and LooseLeaf side by side and runs ruff, `manage.py check`, a missing-migrations check and the tests on every push. Formatting is left as written rather than reformatting every file.

## Phase 2: iPad and offline

**27 Oct 2026. One teacher account, behind one gate.** Phase 2 makes the app reachable from the iPad, so it now needs a password. `django.contrib.auth` holds a single account. `core.middleware.GateMiddleware` applies three gates in order: no account yet → first-run setup (which now starts with "Your account"); signed out → login; signed in with no timetable → setup. An install from before sign-in existed (a timetable but no account) gets an account-only setup and keeps everything else. A signed-out HTMX request answers with `HX-Redirect`, so the whole page moves to the login rather than the form landing inside a sheet. The session lasts 120 days so the iPad never asks mid-lesson. Five wrong passwords from one address pause logins for five minutes. Passwords are at least ten characters. "Delete everything" keeps the account but signs every device out.

**27 Oct 2026. Served by waitress on localhost; Tailscale is the only way in.** `tools\serve.ps1` applies migrations, collects static files, runs Django's deploy checks and serves with waitress on 127.0.0.1, with debug off (debug is now opt-in through `DOWNBEAT_DEBUG=1`). Whitenoise serves static files. Nothing on the school network can reach the port; the iPad comes in through `tailscale serve`, which terminates HTTPS with Tailscale's real certificate for the laptop's `ts.net` name and forwards to localhost. `tools\tailscale-check.ps1` writes that name to `local\hosts.txt`, which turns on the allowed host, CSRF trusted origin, secure cookies, the forwarded-HTTPS header and HSTS. There is no HTTPS redirect, because the laptop itself uses plain HTTP on 127.0.0.1, which never leaves the machine. `tools\install-server-task.ps1` starts the server at Windows sign-in. `docs/TAILSCALE.md` is the step-by-step for the parts done on the devices.

**27 Oct 2026. `queue.js` is one file in two roles.** The project allows one hand-written JS module for the offline queue, "IndexedDB + service worker", but a service worker has to be fetched as its own script. `queue.js` checks where it is running: registered at `/sw.js` it is the service worker; loaded by a page it registers the worker and (from the queue step) holds captures. The server serves it at `/sw.js` with its cache version and precache list filled in. The version is a hash of the app-shell files, so any change to CSS or JS replaces the iPad's copy the next time it is online.

**27 Oct 2026. Caching: shell first, pages network-first with a four-second timeout.** Static files come from the cache. Pages and sheets go to the laptop first and are saved as they load; if the laptop doesn't answer within four seconds (school Wi-Fi) the saved copy is used, and a page never saved shows "Not reachable". Redirects aren't saved (a redirect usually means the session ended). Login, logout, the service worker and Settings → Data are never cached. Saved pages older than three days are dropped. Signing out empties every cache on that device, so the day's lessons can't be read offline by anyone else.

**27 Oct 2026. Icons are drawn by a script.** `tools/build_icons.py` draws a crotchet on the theme's accent from `tokens.resolved.json`, writing the PNGs with the standard library only (180 for iOS, 192, 512, and a 512 maskable with the note inside the safe zone). Rerun it after changing the theme.

**27 Oct 2026. Every room-view capture goes through the queue, online or not.** Notes, free text, spoken to, absence, picker draws, action done, remove and undo each become an operation with an id made on the device, saved to IndexedDB, drawn at once, and sent to `/sync/`. There is one path, so the offline path is exercised every lesson rather than only when the Wi-Fi drops. The Phase 1 endpoints for each button (`note_add`, `spoken_toggle`, `pick` and the rest) and their server-rendered fragments are gone; the inbox stays an online read, since past notes aren't for reading mid-lesson, and shows a calm "needs the laptop" line when out of reach.

**27 Oct 2026. The room view draws from lesson state with unsent captures replayed on top.** The page embeds the lesson as JSON (`notes.state.lesson_state`) and canvas.js draws the seat marks, log, counts, sheets and picker from it, replaying this device's unsent operations through the same rules. On load and after every sync it fetches `/room/<id>/state/`; offline, the service worker answers with the newest saved copy. Confirmed operations stop being replayed only once fresh state that includes them has arrived. Sheets are `<template>`s rendered by Django; names and note text are only ever set with `textContent`.

**27 Oct 2026. Sync is idempotent and last-write-wins, with no operations table.** Adds carry their own UUIDs, so resending creates nothing new. Remove, restore and attendance compare the operation's time with the row's `updated_at`; "spoken to" toggled off deletes only rows made before the tap, so a later tap survives a resend. Notes and spoken-to rows take the time they were caught, not the time they were sent. A device clock more than five minutes ahead is held to now. Operations that can never apply (a deleted lesson, an empty free-text note, an unknown type) are rejected and dropped from the queue with a console warning; everything else waits. A signed-out device gets 401 and keeps its queue until the next sign-in.

**27 Oct 2026. The picker draws on the device.** The draw comes from the lesson state (present pupils not yet spoken to, then everyone), so it works offline and costs no round trip. "<name> is absent" removes that draw's spoken-to row by its id and marks the absence.

**27 Oct 2026. The bottom bar says when captures are waiting, in neutral words.** "3 saved on this device" while unsent, "Sign in to send 3" if the session has ended, nothing otherwise. It is information, not a warning: no colour, no count when there is nothing to send.

**27 Oct 2026. Seat moves are not queued.** BUILD_ORDER lists SeatAssignment in the offline queue, but in Phase 1 seating is only edited in the Plan area at the desk, where the laptop is always in reach, and the room view never moves seats. Queuing plan edits would add conflict handling for no lesson-time gain, so the seating editor stays online-only. Revisit if seat moves ever come into the room view.

**27 Oct 2026. The desk layout starts at 76rem, not 64rem.** UX.md puts the breakpoint "around 1024px" and also says iPad landscape keeps the portrait layout. A common iPad is 1180px wide in landscape, so a 1024px breakpoint would give it the laptop's side panel. The container query is set at 76rem (1216px): every laptop gets the side panel, every iPad except the 12.9-inch in landscape gets the docked sheet. Still a width on the room's own container, never a device check.

**27 Oct 2026. Below desk width the panel is a sheet docked above the bar.** Closed, it is a grab handle and the plan strip, sized to fit them; the canvas keeps a matching clear space at its foot so no seat is hidden. A tap on the handle, its keyboard activation, a swipe up or `L` opens it to at most 70% of the room's height to show the log; a swipe down or the handle closes it. At desk width it is the side column and the log is always shown.

**27 Oct 2026. Laptop shortcuts.** N next lesson, P pick, A actions, U undo, L the log, ? the list. Inside a pupil's sheet, 1–9 record that note type and S, X and F are spoken to, absent and free text, so a note is two key presses after a click on the seat. None fire while typing or (except the sheet keys) while a sheet is open. Hints appear on the buttons only for a fine pointer that can hover, so the iPad never shows them. The list is also in the ⋯ menu.

## Phase 3: flags, relationships, groups, goals

**27 Oct 2026. A `pupils` app holds Phase 3's pupil-side tables and the Pupils area.** The project layout places Rotation in `timetable` but names no home for flags, relationships, groups or loans. They go in a new `pupils` app with the Pupils area pages (class list, pupil page). Goals and the checklist go in `notes`, beside the notes that feed them.

**27 Oct 2026. Flag colours are eight reserved palette slots.** `--flag-1` … `--flag-8` are Tier 3 variables in downbeat.css, written in `oklch()` (no raw hex), with light and dark variants, and kept clear of the interface's indigo accent. A FlagType chooses a slot by number (one flag per slot), never a free colour, so no flag can match a button. On a seat they are a coloured left edge, thin bands side by side when there are several, `aria-hidden` and with no text at all. The label, the note and "what works" appear on the pupil page only; the class list shows swatches without labels; the projector view, the cover PDF and the lesson state carry nothing of flags.

**27 Oct 2026. The first-run setup gains an optional flags section.** As promised in Phase 1. Checklist items join it with the checklist step.

**27 Oct 2026. Delete-all and export are checked against every model.** A test now fails if any model in Downbeat's own apps is missing from the delete-all list or the export, so later phases can't add a table that "delete everything" leaves behind.

**27 Oct 2026. Relationships are stored once per pair.** A Relationship holds its two pupils in a fixed order (a database check enforces it), so "Aleya and Jojo" and "Jojo and Aleya" are the same row, and a pair is either keep-apart or pair-well, not both. They are added on either pupil's page, choosing from pupils who share a class with them, and show on both.

**27 Oct 2026. "Next to" is an ellipse, wider than it is deep.** The data model says adjacency is computed by radius, but a single radius can't fit rooms where desks are 160 units apart side to side and rows 72 apart front to back: any circle that reaches the next desk along also reaches two rows back. Seats are neighbours when their centres fall within an ellipse of about two seat widths across and under two seat depths front to back: a seat either side (even with a gap), the seat in front or behind, but not diagonals across a gap nor two rows away. `rooms/adjacency.py` is the one definition; the editor and the shuffle both use it.

**27 Oct 2026. The seating editor validates as you drag.** After every move the board shows a solid warning line between keep-apart pupils who are neighbours, a quiet dashed line between pair-well pupils who are, a dotted outline on a seat whose pupil's flag rule isn't met, and a one-line summary in words. "Near the front" means the front zone; "near the teacher" means a seat painted near-teacher or within about three seat widths of the teacher marker. Rooms don't record doors or windows, so "near the door" and "away from the window" can't be checked yet and count as met.

**27 Oct 2026. The shuffle never breaks a hard rule; it refuses instead.** `rooms/solver.py` is a pure function over seat ids, pupil ids and constraints. Hard rules: locked seats keep their pupil, and no keep-apart pair are neighbours. Soft goals, scored: each flag seating rule met (10 points), each pair-well pair together (3). It runs forty randomised depth-first searches with backtracking, hardest pupils first (those with rules, then those with most keep-apart partners), and keeps the best-scoring arrangement. If no arrangement can keep every keep-apart pair apart with the seats and locks given, it raises rather than returning a compromise, and the editor says "Unlock someone or add seats". More pupils than seats leaves the least constrained unseated. Property tests (Hypothesis, a dev dependency) generate rooms, classes, relationships, locks and rules and check every returned plan: locked seats unmoved, no keep-apart neighbours, nobody seated twice, everyone seated who fits; and with no hard constraints it never refuses.

**27 Oct 2026. Shuffle rearranges in place; Duplicate keeps history.** "Shuffle" reseats the plan and one Undo puts the whole shuffle back. "Duplicate as a new plan from today" copies the plan (with its locks) as a new plan active from today and ends the original yesterday, so last half term's arrangement stays on record and `SeatingPlan.current` picks the right one for any date. Duplicate first, then shuffle, for a fresh start that keeps the old plan.

**27 Oct 2026. Groups: tints of their own, managed under Plan, ended not deleted.** A class's Groups page (Plan → class → Groups) creates groups with members and optional roles; a pupil is in at most one active group per class. Ending a group keeps it, its members and their roles as history ("which part did they play last unit"); a group with notes can't be deleted. Each active group takes the least-used of six reserved tints (`--group-1` … `--group-6`, Tier 3, pale and low-chroma with dark-mode variants), separate from the eight flag colours: on a seat a group is a background tint and a flag is a saturated left edge, so the two can't be confused. Seats are tinted in the room view and the seating editor.

**27 Oct 2026. Group notes are one note for the group.** Note gains a nullable `group`; a note is for exactly one pupil or one group, and a group note's group must belong to the lesson's class. It is not copied to members: BUILD_ORDER says a group note "fans out to members only when explicitly attributed", and attributing it is a sweep job for Phase 4. The group's sheet is the note sheet without spoken to, absent or the inbox.

**27 Oct 2026. Group chips go in the row under the room, displacing nothing.** The room view shows the class's active groups as tinted chips beside the unseated pupils, only when there are any; nothing on the bar moves. A tap opens the group's note sheet.

**27 Oct 2026. Goals count lessons, not notes.** "A house point in 20 lessons this week" counts lessons (not cancelled, for the goal's class or every class) that got at least one live note of the goal's type, so two house points in one lesson count once. "Each week" runs Monday to Sunday from the goal's start date; "since the start date" runs from it to today. The server sends each goal's count from the other lessons; the room view adds this lesson the moment it has a matching note, so the counter moves offline too. The first two goals that apply show in the bar as "★ 3/20": a plain number, no colour, no warning, however far behind. The data model's goal links to components and reflections come with Phases 5 and 4.

**27 Oct 2026. The checklist is ticked through the queue.** Checklist items are for every class or one class, edited in Settings (and optionally at first run). The bar's "✓ 1/3" opens a sheet of the lesson's items as toggles; ticks are `checklist.tick` / `checklist.untick` operations like every other capture, so they work offline and reset each lesson by belonging to it. With no goals or no checklist items, their counters don't appear at all.

**27 Oct 2026. Co-curricular sessions get a register; lessons don't.** For an ensemble the attendance is the record, so a co-curricular session's bar has "Register 23/24", opening a sheet of every member as a toggle (unmarked or absent → present, present → absent) and an "Everyone here" that marks only the unmarked present. Marks are the existing `attendance.set` operations, so they work offline. A timetabled lesson keeps attendance as absence-only (the note sheet's Absent toggle) and shows no register: it isn't the school register. On the Pupils area's class page, a co-curricular class shows each member's attendance as "at 7 of 9 rehearsals", counting only rehearsals where the register was taken. Co-curricular sessions already sit in Today's list beside lessons, marked as such.

**27 Oct 2026. Rotations: a week list and a slot grid, generated or pasted.** A Rotation's `weeks` are week-commencing Mondays and `slots[w][i]` is the day and period of slot *i* in week *w*; a pupil holds one slot index per rotation (several pupils may share a slot for a group lesson). "Generate" builds the usual pattern (one day, the slots stepping one period later each week, so nobody always misses the same subject); "Paste from a spreadsheet" reads one row per week (`02/11/2026, Tue P1, Tue P2, …`, commas or tabs, a header row skipped) and refuses, with the row number, a period the timetable doesn't have, a cell it can't read or a row with the wrong number of slots. As UX.md says, a rotation surfaces only where it changes what happens in the room: the seat of a pupil who is out greys with a strike and a dashed edge (so it reads apart from absent), the picker skips them, and Today's list says "♪ 2 out". It isn't shown on the pupil page.

**27 Oct 2026. The loan log lives under Pupils.** Pupils → Loans lists what's out (overdue first, marked "(overdue)" in words on this desk page), lends an item that's on the shelf to a pupil with an optional due date, takes it back with an optional condition note (which becomes the item's condition), and adds equipment. A database constraint allows one open loan per item. The pupil page lists what they currently have. No loan appears in the room view.

**27 Oct 2026. "Missing out" is plain counts, fewest first.** A tab on each class in the Pupils area lists its pupils by house points, then spoken-to rows, fewest first, with their absences alongside for context (few house points across many absences is a different story). "This half term" starts at the class's term start if set, otherwise seven weeks back, and the start date can be changed on the page. Only notes and turns from that class's lessons count; removed notes don't. No score, no average, no colour: it is a list to read at the desk, not a warning.

## Phase 4: plans, curriculum skeleton, prep, sweep

**27 Oct 2026. Phases are built in order without waiting for classroom use (continued).** As decided before Phase 2, Phase 4 follows Phase 3 directly, its "Done when" checked against demo data.

**27 Oct 2026. The curriculum lives under Plan; sessions point at lessons.** A `plans` app holds Scheme → Unit → LessonPlan, each lesson with ordered activities (text and minutes) and resources (a path or link, never an upload, with a print flag, copies and a setup note). Plan → Schemes of work edits them; "Duplicate unit" copies a unit with every lesson, activity and resource. Session gains the data model's nullable `lesson` (set to null if the lesson is deleted, so a session's notes outlive any plan). Each class has a page with Lessons, Seating and Groups tabs: Lessons lists the class's sessions from a week ago to six weeks ahead with a lesson for each, and "Fill in order" gives every coming session without a lesson the chosen unit's next lesson, carrying on after the last of that unit's lessons the class already has.

**27 Oct 2026. The panel is Log or Plan; the strip is the flip.** As UX.md has it: with the Log showing, the strip reads "Now: <activity> · 12 min in · Next: <activity>"; with the Plan showing, it is the last log line. A tap on the strip flips them. Where we are in the lesson is worked out on the device from the period's start and the activities' minutes, so it ticks along offline and the current activity is highlighted in the plan. A session without a lesson keeps the plain strip ("P3 · 10:50–11:50") and has no Plan side, so there is never an empty "no plan" panel in the room.

**27 Oct 2026. Tab flips only when nothing has focus.** UX.md says the Tab key flips the panel on the laptop, but Tab is how keyboard users move between controls; taking it over would break keyboard navigation. Tab flips Log and Plan only while nothing on the page is focused (just after a sheet closes, or after clicking the room's background), and otherwise moves focus as normal.

**27 Oct 2026. `hidden` stays hidden inside the room view's panel and sheets.** LooseLeaf's compositions set a display value, which overrides the browser's handling of the `hidden` attribute; a scoped rule restores it, and the docked panel's desk-width rule skips hidden children. No `!important`.

**27 Oct 2026. The sweep is one scroll, and saving it marks the session swept.** Sweep (a top-level area, desk tempo) shows a day's sessions as cards, a tick on those swept and the first unswept one outlined, with previous and next days a click away. A session's sweep is a single page read top to bottom: each activity's status (done, partly, not reached) with "if unfinished, carry to <the class's next lesson>" ticked by default; the lesson's caught notes, each with a Bin tick, and for a group note a "Give to each member" button that makes one copy per member (the explicit attribution BUILD_ORDER asks for; the group note itself stays, and giving twice adds nothing); and one reflection line with optional Teachers' Standards tags. Saving writes ActivityStatus rows, bins the ticked notes, saves the SessionReflection (whose existence is "swept") and marks a planned session taught. Sweeping again updates rather than duplicates; unticking carry takes an activity back. The hinge judgement waits for Phase 5's Check table.

**27 Oct 2026. Carry-forward prompts appear even before the next lesson is planned.** Carried activities go to the class's next session that isn't cancelled. They show in that session's room view Plan panel ("Carried forward … from Tue 27 Oct") and its sweep page, and the panel exists for them even when no lesson has been chosen yet, because a carry-forward is content, not an empty state.

**27 Oct 2026. Prep is generated, saved, and keeps its ticks.** Prep is a tab inside Sweep. It opens on the next teaching day (tomorrow, or Monday after a Friday), and lists each session with what its lesson's resources ask for ("Print 30 × Lyric sheet (Music/Y8/lyrics.pdf)", "Set up: Keyboards: …") and the class's open actions ("Chase: Tariq L · Chase homework"), plus items the teacher adds. Generated items are saved as PrepItem rows so ticks persist; opening Prep brings them up to date with the plans, removing unticked items whose source has gone and never removing a ticked one. Generated items can be ticked but not deleted; manual ones can be both.

**27 Oct 2026. A reflection can spawn a goal.** The sweep's reflection section has an optional "Turn this into a goal" (text, which note type it counts, a target, this class only or every class). Saving the sweep creates a weekly goal starting today and links it from the reflection, which then reads "Became the goal …". The data model puts the link on both tables (`Goal.spawned_from_reflection`, `SessionReflection.spawned_goal`); one foreign key on the reflection carries it, with the reverse available from the goal. An incomplete goal isn't made, but the sweep still saves.

## Phase 5: assessment

**27 Oct 2026. Strands, bands and components are the frame; the unit page holds the components.** An `assessment` app holds teacher-defined Strands and Bands (Settings → Strands, Bands; nothing assumes how many), and each unit's Components (pupil-facing text, a strand, a default next step, optionally the earlier component it builds on) and numbered FeedbackCodes, edited on the unit's "Components and codes" tab. A strand in use can't be deleted. Duplicating a unit now copies its components and codes too.

**27 Oct 2026. Criteria files are JSON, and strands travel by name.** "Download criteria file" writes a unit's components and codes as JSON (`"format": "downbeat-criteria"`, version 1), with "builds on" and code-to-component links as positions in the list. Importing adds them to a unit, matching strands by name and creating any that are missing, and refuses (adding nothing) a file that isn't one, is from another version, or has a component without text or strand. The file is read in memory, never stored.

**27 Oct 2026. Observations: long-press, one tap, next step attached.** A long-press on a seat (half a second, cancelled by moving) opens the observation sheet: the lesson's unit components, each with Not yet / Partly / Secure. A tap saves the observation with the component's default next step and shows it as a confirmation line; "Change" edits it with one more tap, never required. The note sheet also has an "Observe" button (and O on the laptop) for anyone not using a touch screen; it and the long-press only exist when the lesson's unit has components. Observations go through the queue (`observation.add` / `.update` / `.remove`), appear in the Log in time order with the notes, and are listed in the sweep to keep or bin. Rule 4 is held three ways: the sheet always attaches the default next step, sync rejects an observation or edit with no next step, and the database refuses a row with neither a next step nor a recording. A state may move backwards: every observation is kept as it was made, and nothing derives a figure from them. The seat's long-press callout is suppressed on iOS so the gesture belongs to Downbeat.

**28 Oct 2026. The plan strip stops at the end of the period.** Lesson state now carries the period's end as well as its start. After it, nothing is "now": the strip shows the objective (or what was carried in) and no activity is highlighted, as when a period has no times. Found while capturing the documentation screenshots, when the strip read "836 min in" late in the evening.

**28 Oct 2026. Hinge checks: planned on the lesson, asked in the session.** A Check is either planned (on a LessonPlan, at most one per lesson) or asked (on a Session), never both; a database constraint holds it. The planned check is written in the lesson editor: the question, the right answer, up to four wrong answers each with the misconception it shows (a wrong answer without one is refused), and a threshold, 80% by default. The unit's lessons' checks together are the bank, listed on the unit's Assessment tab (renamed from "Components and codes"); a lesson can start from any of them, and duplicating a unit copies them. The data model gives Check a session and no lesson, so `lesson_plan` (nullable) holds the planned ones and `source` links an asked check back to its plan.

**28 Oct 2026. The decision is the record.** When a decision is made, the planned check is copied into the session with the decision and the minutes into the period, so the record keeps the question as it was asked even if the plan is edited later. Before that the session has no check at all. The bar's Hinge button sits after Pick, as UX.md's skeleton has it, so it displaces nothing; it is always there and greyed when the lesson has no check. A tap opens a full-height sheet (question, the right answer marked, each wrong answer with its misconception, a timer from opening, and Re-taught / Moved on / Paired at the foot); one more tap records the decision and closes it. H opens it on the laptop. Decisions go through the queue (`check.decide`, `check.clear`) and appear in the Log; deciding again, from either device, changes the one record if made later. Taking a decision back blanks it rather than deleting the row, so a late resend of the original decision can't bring it back.

**28 Oct 2026. The sweep records the hinge judgement from memory.** A lesson with a planned or asked check has a "Hinge check" section between Caught and Reflection: the question and its misconceptions, "Decided in the lesson, N min in" if it was, and Not asked / Re-taught / Moved on / Paired. A decision made only in the sweep has no minutes.

**28 Oct 2026. Pupils' answers are opt-in per unit, entered in the sweep, and kept only with a decision.** Rule 3 says per-pupil responses are opt-in and off by default, and UX.md puts the opt-in on the unit, so Unit gains `check_responses` ("Record each pupil's hinge answer", off). Entering thirty answers is not a two-tap capture, so it is never in the room: when the unit opts in, the sweep's hinge section has a table of the class with each pupil's answer to choose. Since the decision is the record, answers entered without a decision are not saved and the sweep says so. Sync has no operation for a pupil's answer. The demo school opts its Year 8 unit in, to show the table.

**28 Oct 2026. Feedback is written at the desk, per lesson.** Three-part feedback (done well, to develop, how) is not a two-tap capture, so it lives on a lesson's Feedback page, reached from that lesson's sweep, never in the room. It is for one pupil or one group (a database constraint holds it), optionally against one of the unit's components, and needs at least one of its three parts. A group's feedback shows on each member's pupil page, labelled with the group. The data model calls Feedback "a Note subtype in practice"; it is its own table, since it has nothing of a Note's type, action or badge, and the pupil page lists it in its own section.

**28 Oct 2026. A recording is a path and a moment, and only with permission.** Feedback can point at a recording (a path or link, never uploaded) and a moment in it, typed as minutes and seconds ("1:42" for bar 9). A moment needs a recording, and the database refuses one without. Rule 15: a recording is refused for a pupil without `recording_permitted`, and for a group unless every member has it. `voice_path` waits for voice notes, which have no transcription route yet.

**28 Oct 2026. Feedback codes as a slide.** A unit's numbered codes open as a page of their own: the unit's name and each code's number, words and action in large type, black on white whatever the theme, nothing about any pupil. It opens in a new window to drag onto the projector's screen, from the unit's Assessment tab, a lesson's Feedback page, and the room view's ⋯ menu (only when the lesson's unit has codes), so nothing on the bar moves. It has no full-screen button: rule 9 keeps that for the projector view.

**28 Oct 2026. The class-by-component view shows states and nothing else.** A Components tab on each class in the Pupils area shows a table of the class against a unit's components (any unit the class has been taught, the latest by default): each cell is the pupil's latest observation of that component, in words, with its date and next step on hover. Teacher, self and peer observations are shown separately, the teacher's by default. Rule 5: no totals, averages or percentages anywhere, and the cells are greyscale (an outline for not yet, a shade for partly, solid for secure), since a state is not a grade and the colour palettes belong to flags and groups.

**28 Oct 2026. Self- and peer-assessment are entered in one go from the class list.** A Self and peer tab on each class: choose a lesson (the class's past lessons from units with components), a component and self or peer, then one row per pupil with Not yet, Partly, Secure or None. Each answer becomes an Observation marked with its assessor and carrying the component's default next step, so rule 4 holds for pupils' own judgements too. Pupils left at None are skipped. The teacher's own observations still come only from the seat.

**28 Oct 2026. The pupil page shows feedback and observations.** Below flags, seating and notes, the pupil page lists the pupil's feedback (their own and their groups', newest first, with any recording and moment) and their observations (component, state, next step, and whether it was self or peer). The ipsative timeline comes with recordings in 5.5.

**28 Oct 2026. The class's Pupils tabs are one partial.** List, Missing out, Components and Self and peer share `pupils/_class_tabs.html`, so a new tab is added in one place.

**28 Oct 2026. Feedback can be written whenever.** The teacher's ruling: only the teacher sees the app, so feedback isn't tied to the sweep. It is written from three places: a lesson's feedback page (reached from its sweep or from the room view's ⋯ menu), and the pupil page, where it asks which of the pupil's lessons it belongs to (the latest by default) and offers that lesson's unit's components. The room view itself still opens no feedback form, since rule 1 says an in-lesson capture never opens a form; the ⋯ menu item goes to the desk page, so nothing on the room screen changes.

**28 Oct 2026. The exemplar bank lives on the unit's Assessment tab.** Each exemplar is a unit's recording at a level (low, mid, high), optionally against one component, with a note on what to listen for and, if it is a pupil's work, whose. Only pupils with both `recording_permitted` and `exemplar_reuse_permitted`, and not past their delete-by date, are offered as a source; anything else is refused. Removing an exemplar removes the reference; the file stays in its folder for the teacher to deal with.

**28 Oct 2026. Recordings attach to observations, added from the pupil page.** The data model gives Observation a `recording_path` and lets a recording stand in for the next step (rule 4). The pupil page's "Add a recording" makes one: which of the pupil's lessons (from units with components), the component, the state heard, the path, and an optional next step. It is offered only for a pupil with `recording_permitted`, and refused otherwise. Recordings are paths or links, never uploads (rule 11).

**28 Oct 2026. The ipsative timeline is per component, oldest first.** "Recordings over time" on the pupil page puts the pupil's recordings in order, one line per component (the same piece of work), each with what was heard or said then: an observation's state and next step, or a feedback's words and moment. Group feedback with a recording appears for each member, marked as with the group. Nothing compares the pupil with anyone else. A recording that is a web address is a link straight to its moment (a `#t=` media fragment); a file path is shown to open from the folder.

**28 Oct 2026. Recordings that may no longer be kept are found, not assumed.** Rule 15 says recordings go when a pupil's delete-by date passes, and are kept only with permission. `assessment/recordings.py` finds every reference that breaks that: observations and feedback (including a group's, if any member is affected) for pupils past their delete-by date or without `recording_permitted`, and exemplars from pupils without reuse permission. Settings → Data lists their paths with "Remove these references", and `manage.py purge_recordings` (with `--dry-run`) does the same from the command line. An observation kept only for its recording is deleted; one with a next step keeps it. Since Downbeat never holds the files, the paths are shown once afterwards for the teacher to delete from the folder. It runs when the teacher chooses, not on a timer, so a file is never orphaned without the teacher seeing its path.

**28 Oct 2026. Everything held about one pupil, in one file.** Rule 15 asks for a per-pupil export for a subject access request. "Download everything held about …" on the pupil page gives a JSON file: the pupil, their classes' names, and every row in Downbeat's tables that points at them, found by following each link to Pupil rather than from a list, so a later table can't be left out (a test checks every such model appears). Group feedback they were part of is included. Other pupils appear only by id, never by name.

## Phase 6: summative and reports

**28 Oct 2026. A `reports` app holds Phase 6.** As the project layout has it: summative judgements, the comment bank, export and parents' evenings.

**28 Oct 2026. Judgements are made per unit on the class's Judgements tab, with nothing suggested.** Pupils → class → Judgements shows, for a unit the class has been taught, a table of pupils against the strands the unit's components cover. In each cell: the pupil's latest state (from the teacher's own observations) on each of that strand's components, then the band choices from Settings → Bands, starting at "Not judged", and an optional evidence note. The unit's exemplars are one click above, to listen against. Nothing pre-selects, ranks or proposes a band (rule 6). One judgement per pupil, unit and strand (a database constraint); choosing "Not judged" removes it, and a judgement is re-dated only when its band or note changes, so saving the whole grid again doesn't make every judgement look new. The pupil page lists their judgements.

**28 Oct 2026. Pupil gains an optional UPN.** Rule 10 allows a UPN "used only for export matching"; it is on the pupil's details form, blank by default, and appears only in the report export.

**28 Oct 2026. The comment bank and house style are in Settings → Reports.** ReportSentence holds a sentence for a band in a strand, for one unit or any, with `{name}` for the pupil's first name; nothing is pre-written. The house style is a character limit (blank until the teacher sets it, since the school's MIS limit is still an open question in BUILD_ORDER) and a third-person check, kept in one ReportStyle row made the first time it is saved, so no personal value is seeded.

**28 Oct 2026. A report comment is drafted, then edited and kept.** BUILD_ORDER says the assembled report goes "into an editable field" but gives no table to keep the edit, so a ReportDraft (pupil, class, text) is added. The class's Reports tab shows each pupil's comment: their saved draft, or else a fresh one assembled from the bank's sentence for each band they were judged (the unit's own sentence first, a general one otherwise), followed by their latest feedback's "to develop" and "how". "Draft again" replaces it after a confirmation. The house-style checks are plain warnings under the comment (over the limit, "you", "your", "I", "my", or `{name}` left in), never a block.

**28 Oct 2026. The counter and Copy are attributes, not a third script.** The live character count and the clipboard need a few lines in the browser. The project allows two hand-written modules, both specific (the canvas and the queue), so these are inline `oninput` and `onclick` attributes, as the confirmation prompts already are. Promote-a-note copies before its form submits, so navigating away can't cut the copy short.

**28 Oct 2026. The CSV has no overall column.** The export is name, UPN, a band for each unit and strand the class was judged in, and the comment, with a byte-order mark so Excel reads it as UTF-8. Rule 14 allows one overall figure on explicit export if labelled derived; the project conventions say bands are never computed and nothing averages across components, so none is produced. If the school's system demands one, it is the teacher's to enter.

**28 Oct 2026. Promote a note: copy, then mark.** On the pupil page each note has "Copy for the school system": its words go to the clipboard and the note is marked promoted with the date, once. Nothing is sent (rule 16).

**28 Oct 2026. A parents' evening is defined, then its slots are made.** Pupils → Parents' evenings: a name, date, start and end, minutes per family, a place, and breaks typed as ranges ("18:00-18:15"). Slots run from the start in steps of the slot length, each ending by the close and missing every break. Making them again (after the times change) adds what is missing and removes free slots no longer wanted, but never a booked one. One family per time and one time per family, both held by database constraints.

**28 Oct 2026. Booking is from the class list, two taps, online.** BUILD_ORDER says booking happens "in the room, from the class list, when a pupil turns up with a sheet". The room view is not changed: nothing on it would make way. Instead, while an evening is coming, each pupil on a class's list in Pupils has "Book", which opens their family's free times as large buttons; one tap books and returns to the list. The iPad can open it in the room, but it needs the laptop, since bookings don't go through the offline queue. The evening's own page books from a pupil and time list too, and takes the school's booking export as CSV (time and name per row, matched on first name and initial, one match only), listing every row it couldn't book.

**28 Oct 2026. The night: names in time order, came or didn't, a note.** The "On the night" page lists the booked families in time order, the one due now outlined, each name a link to the pupil page (flags, instrument, observations, feedback, judgements and open actions are all there). "Came" and "Didn't come" are one tap each, with a line for a note from the conversation. "Didn't come" adds an open action, "Follow up with parents: missed …", to the pupil's latest lesson by the evening's date, so it is in the Actions sheet of their next lesson with that class; marking it again doesn't add another. Like booking, it needs the laptop.

## Before the second September: rollover

**28 Oct 2026. The rollover is one review page in Settings, and backs up first.** Settings → Rollover asks, in order: which classes to archive (all, by default); each pupil's year group next year (one up, by default) or whether they have left; which flags and keep-aparts to keep (all, by default, with those set more than a year ago marked "over a year old"); which open actions in the archived classes to carry on (none, by default: each is closed unless ticked, since BUILD_ORDER says to "close open actions or carry them explicitly"); and the recordings past their delete-by date, which are removed. Applying it takes a backup, and does nothing if the backup fails. Flags are shown as their colour with a link to the pupil page, since labels appear nowhere else (rule 8).

**28 Oct 2026. An archived class is kept, read-only.** Class gains `archived_on`. Archiving deletes the class's weekly slots (past lessons keep their date and period), deletes lessons not yet taught, or cancels one that already has something recorded, and ends its groups. Its lessons, notes, observations and seating stay as they were. Sync rejects any capture for its lessons, the seating editor refuses changes, the sweep won't save, and the room view says it is archived. It leaves Plan, the booking lists and the Pupils area's main grid, which lists archived classes underneath. "Bring back from the archive" on the class's Settings page undoes it, though not the slots or lessons.

**28 Oct 2026. A pupil who has left keeps their records.** Pupil gains `left_on`. BUILD_ORDER asks for pupils to be carried forward; it does not say leavers are deleted, and deleting them would also delete the exemplar bank's recordings of former pupils' work. A leaver drops out of pickers and booking lists, and their recordings still go by their delete-by date. Deleting a pupil outright stays in Settings → Pupils, and "Delete everything" ends the lot.

**28 Oct 2026. Pasting a class list reuses the pupils who stay.** Without this, next September's class lists would make a second copy of every continuing pupil. A pasted name is matched to the one current pupil with that first name, initial and (if the class has one) year group, and added rather than created; a name matching two is skipped and listed, to choose from "Existing pupils". A pupil who has left is never matched.
